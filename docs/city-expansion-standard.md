# 城市迁移泛化标准

这份标准用于把当前苏州板块的制作方法，沉淀成后续可复制到任意城市的统一执行框架。

目标不是“再做一份攻略”，而是形成一套可以持续扩城市、扩内容、扩路线的生产标准。

## 1. 总原则

### 1.1 产品目标

每个城市板块最终都要输出 4 类结果：

1. 真实可用的城市内容库
2. 可执行的分天路线
3. 路线级地图联动
4. 路线级住宿联动

### 1.2 内容价值排序

城市内容的价值优先级按下面顺序判断：

1. 是否真实值得去/值得吃
2. 是否能被串进路线
3. 是否信息足够稳定
4. 是否有差异化
5. 是否热度高

### 1.3 生产原则

1. 不依赖用户实时全网搜索
2. 先做精选本地内容库，再做路线生成
3. 路线不是随机拼接，而是规则驱动
4. 小吃、甜品、咖啡不能占用正餐位
5. 城市中明显不同的玩法区必须单独建模

## 2. 城市落地流程

每个新城市统一按 8 个阶段推进。

### 阶段 1：定义城市目标

先明确这个城市在产品里承担什么角色。

必填项：

1. 城市适合玩几天
2. 核心体验是什么
3. 用户为什么要用这个城市板块
4. 这个城市最容易踩的坑是什么
5. 哪一类内容最能形成差异化

输出结果：

- `city positioning`
- `suggest days`
- `must-have experience`
- `avoid pit summary`

### 阶段 2：拆城市玩法结构

把城市先拆成“路线区域”，而不是先堆景点。

每个城市至少要拆出：

1. 核心首访区
2. 生活感补充区
3. 夜景或夜游区
4. 差异化外扩区

如果某个城市存在明显不同玩法，例如：

- 古城 vs 海边
- 城区 vs 山区
- citywalk vs 自驾线

则必须单独建模，不能混在同一条通用逻辑里。

输出结果：

- `areas`
- `area type`
- `fit mode`
- `traffic relationship`

### 阶段 3：建立多源采集池

每个城市统一分 4 类源头采集。

#### 3.1 餐饮与补给

主来源：

1. 大众点评
2. 美团公开页

辅助来源：

1. 微博
2. 公开网页文章

#### 3.2 景点与路线关系

主来源：

1. 高德
2. 公开景区资料
3. 政务/文旅公开页面

#### 3.3 住宿

主来源：

1. 携程
2. 飞猪
3. 智行

#### 3.4 热度与近期状态

辅助来源：

1. 微博
2. 公开搜索结果

说明：

- 社媒类平台只做辅助判断，不直接做唯一真相。
- 受限制强、长期自动化风险高的平台，不作为主生产链路。

### 阶段 4：做内容筛选和分类

采集回来后，不能直接进库，必须先过筛选层。

#### 4.1 景点筛选标准

保留条件：

1. 值得专门去
2. 能被路线串联
3. 时效性可控
4. 不只是“大家都知道”

降权条件：

1. 营销感强
2. 太像单纯打卡点
3. 路线价值弱
4. 已经过度重复

#### 4.2 餐饮筛选标准

必须先分层：

1. 正餐
2. 小吃
3. 甜品
4. 咖啡
5. 茶饮

正餐必须再分菜系或吃法：

1. 本地经典菜
2. 家常热炒
3. 融合菜
4. 火锅
5. 地域特色专项

#### 4.3 住宿筛选标准

过滤规则：

1. 太便宜且质量不稳的过滤
2. 评分明显低的过滤
3. 区域不匹配的过滤
4. 营销感重但路线价值低的过滤

### 阶段 5：落成本地标准化数据

所有城市都统一落到本地标准结构里，方便路线引擎调用。

推荐结构分 4 类：

1. `spots`
2. `foods`
3. `hotels`
4. `day templates`

每条数据的最小字段标准如下。

#### 5.1 景点字段标准

必填：

- `id`
- `type`
- `name`
- `area`
- `latitude`
- `longitude`
- `recommendScore`
- `freshnessScore`
- `marketingRiskScore`
- `suggestStayMinutes`
- `routeRole`
- `updatedAt`

选填：

- `summary`
- `recommendReason`
- `riskTips`
- `bestFor`
- `avoidIf`
- `sourcePlatform`

#### 5.2 餐饮字段标准

必填：

- `id`
- `type`
- `name`
- `area`
- `foodType`
- `avgCost`
- `latitude`
- `longitude`
- `recommendScore`
- `freshnessScore`
- `marketingRiskScore`
- `routeRole`
- `updatedAt`

强制补充标签：

- `mainMeal / snack / drink`
- `cuisine type`
- `fit time slot`

#### 5.3 住宿字段标准

必填：

- `id`
- `type`
- `name`
- `area`
- `nightlyPriceRange`
- `avgCost`
- `recommendScore`
- `freshnessScore`
- `marketingRiskScore`
- `routeRole`
- `updatedAt`

#### 5.4 模板字段标准

每个城市至少要有：

1. 1 天模板
2. 2 天模板
3. 3 天模板
4. 3 天以上补位模板

并且每种模式要区分：

1. `relaxed`
2. `hardcore`

### 阶段 6：建立路线引擎规则

路线生成统一分三层。

#### 6.1 骨架层

先决定：

1. 玩几天
2. 用哪种模式
3. 每天落在哪个区域

#### 6.2 填充层

再按时间槽位填：

1. 上午主线
2. 午餐
3. 下午主线
4. 下午补给
5. 晚餐
6. 夜景或收尾
7. 今晚住宿

#### 6.3 校正层

最后统一做校正：

1. 景点不重复
2. 正餐不重复
3. 连续正餐不同风格
4. 小吃甜品不占正餐位
5. 外扩区餐厅不串到城区主线
6. 住宿和当天区域尽量匹配

## 3. 正餐系统标准

正餐系统是路线质量的关键模块，每个城市都必须单独维护。

### 3.1 正餐池结构

每个城市正餐池至少要有 4 个不同风格层：

1. 城市经典代表
2. 更生活化家常馆子
3. 非同质化补充菜系
4. 城市差异化专项餐饮

举例：

- 苏州：苏帮菜、家常热炒、融合菜、火锅、太湖湖鲜

### 3.2 正餐排布规则

1. 同一天午餐和晚餐尽量不同风格
2. 相邻两天不要重复同一家
3. 相邻两顿不要重复同菜系
4. 同一个区域优先吃本区餐厅
5. 外扩日优先吃外扩区专项正餐

### 3.3 下午补给规则

下午补给只能从下面池子选：

1. 咖啡
2. 甜品
3. 茶饮
4. 小吃

下午补给位原则：

1. 只做节奏缓冲
2. 不抢正餐位
3. 顺路优先
4. 有停留价值优先

## 4. 住宿系统标准

### 4.1 住宿池分类

每个城市住宿统一分：

1. 核心城区住宿
2. 差异化外扩区住宿
3. 高体验度假型住宿

### 4.2 住宿筛选逻辑

1. 评分门槛
2. 价格门槛
3. 区域匹配
4. 路线价值

### 4.3 住宿进路线规则

1. 每个行程日都要有对应“今晚住宿”
2. 多日路线要考虑是否换住
3. 外扩专项日可单独切住宿
4. 地图上必须显示住宿点

## 5. 地图联动标准

每个内容点都必须有经纬度。

地图层统一展示：

1. 景点点位
2. 餐饮点位
3. 住宿点位
4. 每日路径顺序

标准要求：

1. 用户能看懂当天动线
2. 不是只有文字攻略
3. 住宿必须是路径终点之一

## 6. 代码结构标准

后续所有城市，统一按以下思路组织。

### 6.1 数据层

建议放在：

- `utils/travelData.js`
- 或后续拆成 `cities/<city>.js`

### 6.2 逻辑层

建议放在：

- `utils/routePlanner.js`

职责：

1. 根据天数和模式选模板
2. 根据规则生成日程
3. 校正餐饮
4. 校正住宿
5. 输出地图数据

### 6.3 页面层

主要展示：

1. 目的地页
2. 路线页
3. 详情页
4. 地图页

## 7. 新城市执行 SOP

后续每进入一个新城市，严格按下面顺序执行。

### 第一步：城市定位

输出：

1. 适合玩几天
2. 核心玩法
3. 差异化区域

### 第二步：区域拆解

输出：

1. 3 到 5 个核心区域
2. 每个区域的玩法标签

### 第三步：首批采集

每类先收：

1. 景点 12 到 20 个
2. 正餐 15 到 25 个
3. 下午补给 10 到 20 个
4. 住宿 8 到 15 个

### 第四步：内容筛选

输出：

1. 可入库清单
2. 降权清单
3. 暂缓清单

### 第五步：数据落库

输出：

1. 城市基础信息
2. 景点库
3. 餐饮库
4. 住宿库

### 第六步：路线模板

至少先做：

1. 2 天松弛版
2. 3 天松弛版
3. 3 天特种兵版

### 第七步：规则校正

重点检查：

1. 是否有重复景点
2. 是否有重复正餐
3. 是否把小吃当正餐
4. 是否区域串线
5. 是否住宿不匹配

### 第八步：实测验收

每个城市至少验：

1. 2 天松弛
2. 3 天松弛
3. 3 天特种兵

## 8. 城市验收标准

一个城市板块达到可上线标准，至少满足下面条件。

### 内容完整度

1. 有清晰区域结构
2. 有足够景点
3. 有分层餐饮池
4. 有住宿池

### 路线可执行性

1. 路线没有明显重复
2. 午晚餐逻辑正常
3. 下午补给不抢正餐
4. 地图可读
5. 住宿插入合理

### 差异化程度

1. 不只是经典景点堆砌
2. 不只是大众熟知餐厅
3. 有城市独有玩法区
4. 有自有内容判断标准

## 9. 苏州已经验证过的关键经验

以下经验默认进入泛化标准。

1. 城市必须先拆区域，再做路线
2. 差异化玩法区必须单独建模
3. 餐饮必须先分正餐和补给
4. 正餐必须再分菜系和体验类型
5. 模板锚点和规则引擎要同时存在
6. 住宿必须进路线，不是独立列表
7. 地图联动必须从一开始考虑
8. 内容库优先于实时抓取

## 10. 后续升级方向

当前这套标准适合“精选内容库 + 规则路线引擎”阶段。

后续可以继续升级成：

1. 城市内容后台管理
2. 半自动采集与整理
3. 内容更新时间标记
4. 用户自定义替换餐厅或景点
5. 城市间统一评分体系
6. 更细的用户偏好分流

---

一句话总结：

后面做任何新城市，都先把内容做成“标准化本地精选库”，再通过“区域骨架 + 时间槽位 + 餐饮分层 + 去重规则 + 住宿联动”生成路线，而不是临时拼一份城市攻略。
